# Research Methodology — Statistical Hypothesis Testing

Standing capability for testing entry-gate hypotheses against real historical
data, independent of the live scan pipeline. Set up 2026-08-30, first used to
settle the "should the entry gate loosen from 7-of-7 to structural+2-of-3"
question — see [Historical note](#historical-note-why-7-of-7-stays) below.

This is research tooling, not part of the live pipeline. Nothing here is
wired into `daily-scan.sh`, cron, or any order-placement path.

## 1. The isolated `~/venvs/trading-eval` environment

A dedicated Python venv, **outside** this repo and **outside** the system
Python.

**Why isolated, specifically:** `daily-scan.sh` invokes `python3` directly
against the system interpreter (no venv) — see its `prescreen.py` call. A
global/system-wide `pip install` of a research framework's dependency tree
(pandas/numpy/yfinance pins) can silently version-shift the interpreter the
19:00 cron scan depends on. A bare global `pip install` is blocked anyway on
this machine by PEP 668 (`externally-managed-environment`) — the isolated
venv is both the safe path and the only path that doesn't fight the OS.

**To recreate it** (e.g. on a new machine, or after it's been deleted):

```bash
python3 -m venv ~/venvs/trading-eval
source ~/venvs/trading-eval/bin/activate
pip install --upgrade pip
pip install -r ~/Projects/aria-trading/scripts/research/requirements.txt
```

Pinned versions (as installed 2026-08-30): `investing-algorithm-framework==8.10.0`
(deliberately the stable release, **not** the `9.0.0aXX` alpha — v9 has
breaking API/format changes and wasn't installed), `pandas==3.0.5`,
`numpy==2.5.2`, `yfinance==1.7.0`.

## 2. Role of `investing-algorithm-framework` (IAF)

IAF is used **strictly as an isolated statistical research tool** — walk-forward
window generation and (where wired up) permutation testing — to validate
**directional/structural edge** on the underlying. It is explicitly **not**:

- an options P&L engine (that's `scripts/backtest/`'s vendored Black-Scholes
  spread simulator — `run_bps_backtest.py` + `options_portfolio.py` — the
  authoritative source for spread-level win rate / P&L / drawdown / Sharpe)
- wired into live trading, order placement, or the daily scan in any way
- a source of truth on its own — every finding from it should be read
  alongside the Black-Scholes P&L backtest's result on the same question,
  not in isolation (see the historical note below for why this matters)

IAF's real API only exposes what the **installed v8.10.0** provides —
`generate_rolling_backtest_windows` / `BacktestDateRange` /
`analyze_backtest_windows` for walk-forward window splitting. Its
`BacktestPermutationTest` dataclass exists but is coupled to running a full
`App`/`Algorithm`/`TradingStrategy` order-and-portfolio simulation to
produce the `BacktestMetrics` it permutes — heavier than needed for a
directional-only question. The custom statistic used in section 3 below
(MA150 forward survival) is computed directly in plain Python/pandas; IAF
supplies only the walk-forward window boundaries, and a hand-rolled
two-proportion permutation test (numpy, no new dependency) supplies the
significance test. **v9.0-alpha** adds a genuine `Study`/`Universe`/
`BacktestWindow`/Monte-Carlo-permutation API that would remove the need for
the hand-rolled test — worth revisiting if/when v9 stabilizes.

## 3. `scripts/research/iaf_ma150_survival_bridge.py`

**What it evaluates:** for a given entry-gate tier, the probability that a
signaled ticker's close stays above that signal day's MA150 value for the
*entire* following 30 trading days (a strict "never dips below the line even
once" bar, not "closed above at day 30" — see the caveat below). Compares
two tiers side by side: `current` (the live 7-of-7 `entry_checks()` gate,
`min_structural=None, min_confirm=None`) vs the **incremental** signals that
`structural_2of3` (`min_structural=4, min_confirm=2` — all 4 structural
checks required, only 2 of the 3 confirmation checks) adds beyond current —
i.e. `conf_s23 and not conf_curr`. This distinction matters: 7-of-7 is a
strict subset of structural+2-of-3 (an all-7 pass trivially satisfies
"structural + ≥2-of-3 confirm" too), so counting a signal in both pools
would compare a group against itself-plus-extra — a real bug in the first
version of this script that CodeRabbit caught 2026-08-31 (see the historical
note's corrected numbers below). Comparing against the exclusive/incremental
signals is also the more decision-relevant question: does what loosening
*adds* hold up, not a self-referential one. Both tiers call the exact same
`scripts/signal_core.entry_checks()` the live scanner uses (imported via
`sys.path`, not duplicated), across walk-forward windows generated by IAF,
over the full `data/universe.csv` universe.

**Read the numbers correctly — three caveats, all found in CodeRabbit's
2026-08-31 review of this script, none of them changed the "not
significant" verdict:**

1. **Strict yardstick.** Because signals trigger near support by
   construction (`near_ma150_support` allows 0–10% above MA150), a routine
   1-day wobble counts as "not survived" even when nowhere near the actual
   short strike (which sits below MA150 with real cushion). Pooled survival
   rates around 43–44% for *both* tiers reflect this strict definition, not
   "half our trades are in trouble." The tool is for **comparing tiers
   against each other** under one consistent strict definition, not for
   reading the absolute percentage as a real-world trade success rate.
2. **Survivorship bias in the universe.** `data/universe.csv` is today's
   membership/market-cap snapshot, applied retroactively across 2023–2026
   windows — a ticker that grew into the $10B–$5T band only recently, or
   that was in-band earlier but has since shrunk/delisted, is tested
   inconsistently with what a live scan would actually have seen on those
   historical dates. Both tiers are drawn from the same (biased) universe,
   so the bias is shared and the *relative* comparison between tiers still
   holds — but the *absolute* survival rates should not be read as a clean
   historical simulation. Fixing this properly needs point-in-time
   constituent snapshots per window, which is a real project, not a
   same-session patch — noted here so it isn't silently assumed away later.
3. **Temporal/ticker clustering.** The permutation test in
   `run_permutation_test()` treats every (ticker, date) outcome as an
   independent draw. In reality, nearby signal dates on the same ticker (or
   correlated moves across tickers in the same window) aren't independent —
   this makes the test *anti-conservative* (more likely to find a
   significant difference than a properly clustered/block-resampled test
   would be). Since the test found **no** significant difference despite
   this bias working in the direction of finding one, the "not significant"
   conclusion is if anything reinforced, not undermined, by this
   limitation. A proper block-bootstrap version is a future improvement,
   not required to trust this run's direction.

**To run it:**

```bash
source ~/venvs/trading-eval/bin/activate
python3 ~/Projects/aria-trading/scripts/research/iaf_ma150_survival_bridge.py
```

Optional flags (defaults shown): `--universe <path>` (default
`data/universe.csv`), `--start-date 2022-01-01` (data download start, 1yr
warm-up before the walk-forward range), `--walk-start-date 2023-01-01`,
`--train-days 365 --test-days 90 --step-days 90` (IAF rolling-window
sizing), `--forward-days 30` (the survival horizon), `--permutations 10000`.

Takes roughly 2 minutes end to end against the full ~750-ticker universe
(most of it is the batched yfinance download).

To test a **new** hypothesis later (a different gate tier, a different
forward horizon, a different survival definition): copy this script as a
starting point rather than editing it in place if you want to keep this run
reproducible — the walk-forward window-splitting and permutation-test
plumbing (`run_permutation_test()`) is reusable as-is.

## Historical note: why 7-of-7 stays (2026-08-30 findings)

Two separate tests, same day, both pointing the same direction:

1. **Black-Scholes P&L backtest** (`scripts/backtest/run_bps_backtest.py`,
   36-ticker/3-year window): current 7-of-7 gate — 24 spreads, 87.5% win
   rate, +$95.49 avg P&L/spread, Sharpe 0.877. Loosen to structural+1-of-3:
   239 spreads, 80.3% win rate, **-$11.80 avg P&L/spread**, Sharpe -0.177.
   Structural+2-of-3: 147 spreads, 79.6% win rate, **-$13.11 avg**, Sharpe
   -0.083. Both looser tiers flip net-negative despite a win rate barely 7-8
   points lower than the strict gate.
2. **This IAF bridge script** (744-ticker universe, 10 walk-forward windows,
   2023–2026): structural MA150 survival rate is statistically identical
   between tiers — 43.58% (current, 319/732) vs 43.22% (structural+2-of-3
   incremental signals only, 2999/6939), diff +0.36pp, p=0.87 two-sided,
   not significant. (First-run numbers, before the double-count fix
   described in section 3 above, were 43.58% vs 43.25% on an overlapping —
   not incremental — s23 pool; direction and conclusion unchanged by the
   fix.)

**The combined read:** loosening the confirmation checks (volume, candle
pattern, RSI-rising) does *not* make the underlying more likely to drift
away from support — frequency of structural weakness is unchanged. But it
does destroy the spread's P&L edge. That rules out "the looser gate just
lets in more names that wander off support" as the mechanism. What's left:
the confirmation checks are gating something the structural checks alone
miss — likely entry-timing/premium quality, or the *severity* of the
support breaches that do occur (a volatility-crush / bad-fill kind of
failure) rather than their frequency (pure directional drift). The 7-of-7
gate is kept not just because it backtests better, but because these two
independent tests together localize *why*: the edge lives in confirmation
quality, not in avoiding drift.
