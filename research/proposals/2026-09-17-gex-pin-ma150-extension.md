## 1. Hypothesis

**Origin, stated honestly:** inspired by eyeballing a commercial visual-TA indicator suite (GAPALGO) that appeared to mark mean-reversion-exhaustion zones. No GAPALGO code or logic was inspected. Everything below is reframed in this system's own VRP/GEX vocabulary. Per the roadmap, `signal_core.py` (v1 EMA150/RSI/candle) stays off-limits as a tuning target.

**Mechanism claim — explicitly labeled as an assumed prior, not an established premise (Fable's correction):** the hypothesis assumes, without independent proof, that an entry more extended above its EMA150 gate carries more terminal price risk against the short strike than a less-extended one, all else equal. This proposal does not establish that premise; it is the working prior the GEX filter is hypothesized to offset. If the primary result comes back null, "extension doesn't add risk in the first place" is a live alternative explanation, not ruled out by this design.

**MA150 disambiguation, corrected (Fable's algebra catch — the EMA switch reduces but does not eliminate the confound):** `vrp_only`'s entry gate is `ema(signal_closes, 150)`; the strike anchor is `short_strike = floor(sma(signal_closes, 150) / 5.0) * 5.0`. Defining `strike_cushion := close - short_strike`, algebra gives:

```
close - EMA150 = strike_cushion + (short_strike - EMA150)
```

verified directly: `close=212.22, short_strike=190.0, ema150=191.5` → LHS `20.72` = RHS `20.72`. So `z_ma150` (built on `close - EMA150`) is **not** independent of cushion — it decomposes into cushion plus a `(short_strike - EMA150)` term that is usually small (SMA150 and EMA150 track each other) but not held constant, and can diverge meaningfully on individual tickers (the same SMA/EMA divergence that caused the 2026-09-14 BX false-PRIME incident). **Fix, since a fully orthogonal extension metric is out of scope for this proposal:** cushion is tracked via an unconditional, pre-registered stratified breakdown (Section 4), computed for every arm regardless of whether the raw means look different. **Wording correction (third-round Fable review):** this stratification is a diagnostic that can expose cushion as a competing explanation — it does not itself control for or eliminate the confound. Any result must be read alongside the stratified breakdown, not treated as confound-free because the breakdown exists.

**Regime-conditional exit label, unchanged from the first revision:** `compute_exit_signal_v2.py` sets `stop_mode = "HARD_STRUCTURAL"` for `NEGATIVE` regime, `"PREMIUM_MULTIPLE"` for `POSITIVE` — the production exit engine's `STRIKE_BREACH` label is regime-conditional. The primary metric (Section 4) still avoids this entirely by using a frozen, regime-independent measurement — see the acknowledged scope change to that measurement below.

**Naming caveat, unchanged:** `gex_regime()`'s `POSITIVE`/`NEGATIVE` name regime *character* (percentile rank vs. trailing 252 sessions), not a direct read of dealer net gamma sign.

**Falsifiable claim, narrowed (Fable's correction — "adds value," not "interaction"):** the first revision's claim ("combined arm's improvement exceeds what either single-factor arm achieves alone") implicitly claimed a synergistic interaction, which two independent additive effects could also produce without any real interaction between extension and GEX. Narrowed claim, defensible by the 4 overlapping (not disjoint) arms this design actually has: **the combined arm's `breach_at_expiry` rate is lower than both the extension-only arm's rate and the GEX-only arm's rate** — i.e. combining the two filters adds value over using either alone. This does not claim, and this design cannot establish, that extension and GEX interact synergistically; a true interaction test would need four disjoint extension×GEX cells and a comparison against the additive prediction, out of scope here given the declared 8-series budget (Section 3).

## 2. Parameter family

- `z_ma150 = (close - ema150) / (close * stdev(daily_log_returns, 20))`, off EMA150 (Section 1 explains this reduces, not eliminates, the cushion confound — diagnosed via the `cushion_pct` stratification in Section 4, not eliminated by this definition alone).
- Swept family: `z_threshold ∈ {1.5, 2.0, 2.5}`.
- **Not swept**, held at production defaults: `gex_percentile_threshold = 0.10`, `gex_lookback = 252`.
- **Four overlapping arms per threshold** (not disjoint — see Section 1's interaction-claim narrowing):
  1. **Baseline** — unfiltered `vrp_only` entries (`vrp_ratio >= 1.1`). Threshold-independent.
  2. **GEX-only** — baseline ∩ `gex_regime == POSITIVE`. Threshold-independent.
  3. **Extension-only** — baseline ∩ `z_ma150 >= z_threshold`. One series per threshold.
  4. **Combined** — baseline ∩ `z_ma150 >= z_threshold` ∩ `gex_regime == POSITIVE`. One series per threshold.
- **Entry-set construction, made explicit (Fable's catch):** all 4 arms are constructed by **filtering a single `vrp_only` entry list**, generated once with the production-default `suppress_reentry=True`. Arms are never independently regenerated with `suppress_reentry` re-evaluated per arm. This design answers "among these specific historically-generated entries, does the filter reduce breach risk?" — it does **not** answer "what would the strategy's full entry set look like if this filter were baked into entry selection itself" (which could unlock different, later entries once the `open_until` reentry-lockout no longer blocks them under a narrower filter) — that is a different, more expensive question, deferred to a later proposal if this one clears Section 7.

## 3. Search budget

**8 series total, maximum**: 2 threshold-independent (baseline, GEX-only) + 2 arms × 3 thresholds (extension-only, combined) = 8. No further sweeping, no new threshold or arm added after seeing results.

## 4. Objective tradeoff

**Primary metric — objective change acknowledged explicitly (Fable's correction):** `breach_at_expiry = close_at_expiry < short_strike`, evaluated at the position's ~30 DTE expiry. This is a deliberately **different question** from "did the trade get stopped out during its life" — the original framing (safety net for the short put to "decay safely") was about stop-out/intraperiod risk, not terminal ITM-ness. Terminal breach was chosen specifically to sidestep the production exit engine's regime-conditional label (Section 1); it does not by itself validate the "decay safely" framing.

**Secondary, reported alongside primary, partially restores the original question:** `ever_breached_intraperiod = any(daily close < short_strike over the holding period)`. Does not gate PASS/FAIL on its own but must be reported per arm; a PASS on `breach_at_expiry` paired with a much worse `ever_breached_intraperiod` rate is flagged explicitly as evidence the filter helps terminal outcomes without helping the "safe decay" claim the hypothesis actually originated from.

**Right-censoring and missing-price protocol, corrected (third-round Fable review — the prior "next available session" rule silently extended holding periods and could cross the OOS cutoff):**
- **Modeled expiry session, defined via the trading calendar, never extended forward.** The engine always constructs `expiry_ts` as a nominal Friday (`entry_ts + 30 days`, rolled forward to the next Friday — confirmed in `bps_signal_engine_v2.py`'s `generate()`). The *modeled expiry session* for pricing purposes is that Friday if it is a real trading day (checked against `us-market-holidays.txt`, the same table used elsewhere in this repo); if the nominal Friday is a market-wide closure, walk **backward** one calendar day at a time to the nearest actual trading session — matching how listed-option settlement actually works (settles on the last session at or before nominal expiration, never after). This never extends the holding period; it can only shorten it by a day or two around a holiday.
- **Separately, a data gap** (the modeled expiry session is a real trading day market-wide, but *this specific ticker's* price series is missing that exact session) is **not** bridged by searching forward or backward for a substitute. That trade is **excluded from the analysis set entirely**, counted separately from the OOS-cutoff exclusion below (two distinct diagnostic counters: `excluded_oos_cutoff` and `excluded_missing_terminal_price`).
- Any candidate whose modeled expiry session falls **after** the last available OOS session (2026-07-24, per Section 6) is excluded the same way — `excluded_oos_cutoff`, reported per arm.

**Cushion diagnostic, unconditional, and in percentage terms (third-round Fable review — wording softened, raw dollar cushion isn't comparable across price levels):** `cushion_pct = (close - short_strike) / close` at entry is computed for every arm and binned into terciles (cut points computed once on the pooled baseline distribution, applied identically to every arm). `breach_at_expiry` rate is reported **both** raw and cushion_pct-tercile-stratified. This is a **diagnostic that can expose cushion as a competing explanation** — it is not a claim that the confound has been eliminated or controlled for; a result should be read alongside the stratified breakdown, not treated as confound-free because the breakdown exists. Both versions are pre-registered outputs; neither may be selectively invoked after seeing which one looks better.

**Business-relevance P&L metric — holding policy and inputs fully frozen in Section 5 (third-round Fable review — Section 5 previously only specified skew/curvature/commission, not enough to reproduce a PASS/FAIL).** Hold-to-expiry only, no simulated early exit or stop of any kind, 1 contract/signal. Must not be worse than baseline for a PASS; not the primary falsification metric (Section 7).

## 5. Cost model

**Fully frozen (third-round Fable review — the prior version pointed Section 4 here but only listed skew/curvature/commission, not enough to reproduce a result):**

- **Pricing engine:** `options_portfolio.py` Black-Scholes, theoretical mid-price fills, no bid/ask crossing simulated — same known limitation the Ghost System exists to eventually validate, inherited honestly.
- **Options config — exact values, sourced from `exit_aware_full_universe_backtest.py:114-120`'s `OPTIONS_CONFIG`, the config this exact backtest family already uses, not re-derived:** `risk_free_rate = 0.045`, `contract_multiplier = 100.0`, `exercise_style = "american"`, `iv_skew = -0.15`, `iv_curvature = 0.05`.
- **Commission:** flat `$1.30`/spread, open-side only, per `run_exit_rule_ab_test.py`'s convention (matches `heap_allocator_sim.py`'s floor).
- **IV dataset and field, exact:** `scripts/backtest/run_out_dolthub_iv/volatility_history.pkl` (`DEFAULT_IV_HV_CACHE_PATH` in `bps_signal_engine_v2.py`) — a trusted local pickle, no re-fetch, no forward-fill. Fields `iv_current`/`hv_current`.
- **Observation timing:** IV/HV observed as of the **signal bar's own date** (`dates[i]`), one bar before the entry/fill bar (`dates[i+1]`) — confirmed in `generate()`'s `vol_by_date` lookup — never same-day as the fill, matching this engine's existing look-ahead discipline.
- **Entry underlying price:** fill at the entry bar's **open** (`price_mode: "open"`, confirmed in the engine's own emitted signal dict) — not the signal bar's close, not the entry bar's close.
- **Missing-IV policy:** no separate downstream handling needed — `BullPutSpreadSignalEngine._vrp_ratio()` already returns `None` for missing/NaN/nonfinite/non-positive IV or HV, and any candidate with `vrp_ratio is None` is already excluded at entry-generation time (`skipped_missing_iv` counter). Every entry in the baseline pool this proposal filters already has valid IV/HV by construction; this proposal adds no new missing-IV branch.

## 7. Stopping rule

For each `z_threshold`, using the frozen `breach_at_expiry` metric (Section 4), after applying the right-censoring exclusion (Section 4):

- **Effect direction, fixed explicitly (Fable's catch — the prior draft's sign was ambiguous and risked accepting the wrong direction):** `improvement := baseline_rate - combined_rate`. A **positive** `improvement` means the combined arm breaches less often than baseline — the desired direction for a short-put seller. PASS requires `improvement`'s point estimate `>= 5pp`, never the unsigned or inverted difference.
- **`n >= 30` is a screening floor, not an evidence threshold.** At n=30, one flipped trade moves the observed rate by 3.33pp — comparable in size to the 5pp bar itself. Below n=30 combined-arm trades: automatically `INCONCLUSIVE`.
- **Uncertainty via a moving-block bootstrap, block length corrected (third-round Fable review — calendar-month blocks understated cross-boundary dependence: a trade entered Jan 31 and one entered Feb 1 can share almost their entire ~30-day holding period, yet would land in different non-overlapping month blocks and be resampled as if independent):**
  - Block length: **45 calendar days**, predeclared now, fixed, never selected after seeing which length produces a PASS. 45 days exceeds `TARGET_DTE = 30` (confirmed constant in `bps_signal_engine_v2.py`) with a 15-day margin, so any two trades whose entries are within one holding period's length of each other are captured within at least one shared block.
  - Block construction: **moving/overlapping** blocks — a block may start on any calendar day within the OOS window, not only month starts (standard moving-block bootstrap, not a fixed monthly partition).
  - Block assignment: each trade is assigned to the block(s) containing its **entry** date (well-defined, always inside the OOS window by construction — unlike expiry, which can be censored per Section 4).
  - Resampling: draw block start-dates **with replacement**, enough blocks to cover the OOS window's length; the **same resampled set of block start-dates is applied identically to all 4 arms within a given bootstrap iteration** (never resampled independently per arm) — preserves the shared-market-condition pairing, since the combined arm is a subset of baseline.
  - Repetitions: 10,000 iterations.
  - Confidence level: 95% (2.5th/97.5th percentile of the bootstrapped `improvement` distribution).
  - **Acknowledged limitation, stated rather than hidden:** 45 days is a predeclared, defensible choice (exceeds the trade horizon with margin) but is still an approximation of the true dependence structure, not a proof of adequate block length — if this proposal reaches implementation and the result is borderline, that borderline-ness should be reported as such, not resolved by trying a different block length after the fact.
- **Narrowed claim (Fable's correction, Section 1):** PASS additionally requires the combined arm's `breach_at_expiry` rate to be lower than **both** the extension-only arm's rate and the GEX-only arm's rate — establishing "combining adds value over either filter alone," not a claimed interaction effect.
- **Multiplicity, declared explicitly (Fable's catch — previously unaddressed):** the 3-threshold sweep is **exploratory**, not Bonferroni-corrected. Any single threshold's PASS is a screening signal, consistent with the "worth forward-testing" framing below — not treated as independently confirmatory evidence, and not entitled to the same trust a single pre-committed threshold would carry.
- **PASS**, all of: `n_combined >= 30`; 95% bootstrap CI on `improvement` has lower bound `> 0`; point estimate `>= 5pp`; combined arm beats both single-factor arms (narrowed claim); P&L not worse than baseline (Section 4). **PASS means "candidate worth moving to the Ghost System's forward pipeline for real confirmation-track data" — not that the hypothesis is confirmed, and does not authorize any live-parameter change.**
- **INCONCLUSIVE**: `n_combined < 30`, or the bootstrap CI includes zero.
- **FAIL**: otherwise.

If more than one threshold PASSes, the accepted candidate is the **lowest** passing `z`. If none PASS, the hypothesis is rejected under this design — no further thresholds, no re-run against a different window, no swap of the GEX-percentile default to hunt for a pass. All-`INCONCLUSIVE` is a valid, final outcome.

**Registration mechanics, unchanged from the prior revision:** `RegistrationRunner.register()` only writes the ledger row; `run()` (`register()` then `_execute_process()`) executes immediately. Registered via `python3 research/registration_runner.py --proposal research/proposals/2026-09-17-gex-pin-ma150-extension.md -- <test command>` once the test script exists.

## Results (Development screening, not confirmation)

Final registered run (`20260917T133819Z_401cae621e62`, fourth attempt, ledger `research/runs.csv`): **z=1.5 accepted** (lowest passing threshold). OOS, all three thresholds PASS per the frozen protocol (n≥30, bootstrap CI lower bound >0, ≥5pp improvement, combined beats both single-factor arms, mean P&L not worse than baseline).

Per this proposal's own Section 7: **PASS means worth moving to the Ghost System's forward pipeline. It does not confirm the hypothesis, does not establish a dealer mechanism, and does not authorize any live-parameter change.**

**Restrained reading of the economics, corrected after review (do not overstate):**
- At z=1.5, OOS: baseline breach 13.96%/$13.83 mean, extension-only 8.73%/$10.99, combined 7.92%/$17.60. Extension does most of the breach-rate reduction; combined's incremental breach improvement over extension-only alone is modest (0.81pp).
- **Combined does not have the best per-trade P&L of all arms** — `gex_only` (no extension filter at all) shows $19.08/trade OOS, higher than combined's $17.60. Combined's case is a lower breach rate than either single filter, not the single highest-earning arm; earlier framing in this thread overstated GEX's economic role by comparing combined only against baseline and extension-only, never against gex_only.
- **No verified mechanism for why extension-only underperforms baseline on mean P&L.** An earlier draft speculated this reflects "thinner, cheaper spreads" from selecting the most-extended entries — that speculation is retracted here; it was never checked against a credit-vs-terminal-loss breakdown, which this script does not compute. The correlation (extension-only's mean P&L is below baseline) is observed; the cause is not established.
- **IS/OOS instability, reported not resolved:** the incremental effect of adding GEX to extension-only flips sign between windows at z=1.5. IS: extension-only $15.99/trade → combined $12.74 (GEX *hurts* IS). OOS: extension-only $10.99/trade → combined $17.60 (GEX *helps* OOS). Per this proposal's own protocol (Section 6/7), IS is not used for scoring and this does not alter the OOS-only verdict above — but a result whose sign flips between adjacent windows warrants real skepticism about how robust it is, not just a passing mention.
- **Reproducibility is incomplete, not fully preserved.** All four registered attempts in `research/runs.csv` share the same `git_head` with `git_dirty=True` throughout (no intermediate commits) — git history alone cannot distinguish which of the four meaningfully different script versions (three real bugs found and fixed across three review rounds: a total-vs-mean P&L gate error, a GEX-evaluated-at-entry-date-not-signal-date error, and a missing `ci[0]>0` guard letting a confidently-negative CI pass) produced which run's numbers. `print_input_hashes()` covers only the IV/HV and OHLCV input *data* files, not the script's own content, the GEX cache, the universe file, or the holiday table. The run logs (`research/runs/*.log`, now committed) plus this proposal's Revision Log are the only record of what changed between attempts — not a substitute for a real content-hash-per-run provenance scheme, which this phase does not have.
